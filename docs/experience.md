# Experience: every interaction we have had with cvc5

One entry per episode, oldest first, numbered `E1` upward. An episode is a
**concrete interaction with cvc5** — a defect we reported, an ask cvc5 accepted
or rejected, a question cvc5 put to us, or a claim of ours about cvc5's code
that turned out to be false. Each is self-contained and carries what we learned
from it.

Ids are allocated above the highest ever used and are never reused. Nothing is
edited away: an entry that turned out wrong gains a later entry correcting it,
and both stay. Instructions for adding one are at the foot.

This is not the record of an observation — that is `bug_db/`, which holds
identities, dates, archived evidence and the `closed_*` fields a closure adds.
The open hypotheses that have not yet become an episode are the register in
`docs/README.md`.

**8 of 13 are negative, and every one of those is ours** — a claim we published
about cvc5's code that was wrong, or an ask that should not have been made. That
ratio is the useful thing on this page, and it is moving in the direction that
matters: the first five were caught by us before cvc5 ever saw them, and the
later ones by cvc5 disagreeing with something we actually sent.

## E1: we pinned every published number to a commit nobody could fetch

| | |
| --- | --- |
| **When** | before the first recorded run, 2026-09-16 |
| **Kind** | negative — ours, and it voided a promise |
| **Ours** | every number in the document set |
| **cvc5** | `16c4001e53`, on the `ajreynol/CVC4` fork |
| **Outcome** | corrected; pinned, tested and enforced in CI |

**What happened.** Every figure published here was measured against
`16c4001e53` and quoted as though anybody could check it. That commit is not on
`cvc5/cvc5` — it is on a personal fork — so no reader could fetch it, and the
promise that *every claim is re-checkable without us* was void for the whole
document set. The measurements happened to be sound: all eight ratchets are
clean at upstream `40a4bb7e4`. Nothing measured was wrong and nothing was
checkable.

**What we learned.** A number and the revision it was taken at are one object,
and the second half is the half that rots silently. The fix was mechanical —
`scripts/cvc5.lock` pins the revision, `tests/test_pin.py` enforces that no
document quotes another, and a CI job deepens a fetch until the pinned commit
appears and fails if it never does, so a fork-only pin cannot pass again.

## E2: our baselines named an `InferenceId` cvc5 has never had

| | |
| --- | --- |
| **When** | before the first recorded run, 2026-09-16 |
| **Kind** | negative — ours, and the ratchets caught it |
| **Ours** | `tests/baselines/infer.json`, `tests/baselines/inferid.json` |
| **cvc5** | `SETS_RELS_TCLOSURE_DOWN`, which did not exist at the time |
| **Outcome** | corrected; baselines regenerated by running the tools |

**What happened.** Running all eight ratchets against the commit they were
recorded at, two failed. Not because cvc5 had changed: our baselines named
`SETS_RELS_TCLOSURE_DOWN` as an id cvc5 emits. `git log --all -S` found it in no
commit in cvc5's history, and the enum at `40a4bb7e4` carried
`SETS_RELS_TCLOSURE_FWD` and `_UP`. The baselines had been **written rather than
generated**.

**What we learned.** A ratchet earns its place by failing when something it
asserts stops being true, and the first thing ours caught was us. That is a
smaller claim than we would have liked to make and a better-evidenced one. A
baseline that was typed is a claim with no measurement behind it, whatever file
it sits in.

## E3: our own delta would have reported a cvc5 rename as improved proof coverage

| | |
| --- | --- |
| **When** | before the first recorded run, 2026-09-16 |
| **Kind** | negative — ours, and it was the dangerous kind |
| **Ours** | `dokimasia.infer baseline --check` |
| **cvc5** | any renamed `InferenceId` |
| **Outcome** | corrected; the two cases are now distinguished in the output |

**What happened.** When an id left the unhandled set, the tool reported it as
*now reconstructed*. An id leaves that set for two unrelated reasons: the theory
has started proving it, or it is no longer emitted at all. The tool could not
tell them apart, so it stood ready to report a **rename in cvc5 as an
improvement in cvc5's proof coverage**.

**What we learned.** This is exactly the class of unbacked claim about somebody
else's code this repository exists in order not to make, and it was in our own
delta rather than in a finding. The output now marks the second case `?` and
says *no longer emitted, NOT reconstructed*, because the honest report of an
ambiguity is the ambiguity, not whichever reading flatters us.

## E4: we published the proof checker's trusted surface as 74% of `src/`

| | |
| --- | --- |
| **When** | while drafting `tcb-001`, before 2026-09-18 |
| **Kind** | negative — ours, retracted before it was carried |
| **Ours** | `dokimasia.tcb measure`, in `exec` mode |
| **cvc5** | the internal proof checker's include closure |
| **Outcome** | retracted; the real figure is **8.0%**, and a test guards it |

**What happened.** The first TCB measurement followed each reached header to its
`.cpp`, as a proxy for *what could execute*. The closure saturates at cvc5's
whole link unit: an unrelated seed, `printer/printer.cpp`, gave the identical
figure. A measure that returns the same answer for every seed measures nothing.
The compile-time surface — the number that discriminates — is 179 files, 41,446
lines, 8.0% of `src/`.

**What we learned.** *What could execute* is a call-graph question and an
include graph cannot answer it. The saturating mode is kept, warns, and is no
longer the default, because a negative result somebody can reproduce is worth
more than a quietly deleted one. `tests/test_tcb.py` guards the corrected
figure.

## E5: we called `set.filter` a safe-mode contract violation, and one command killed it

| | |
| --- | --- |
| **When** | before the first recorded run, 2026-09-16 |
| **Kind** | negative — ours, and the most instructive miss so far |
| **Ours** | `s-6`, a rank-1 candidate |
| **cvc5** | `SETS_FILTER_UP` / `SETS_FILTER_DOWN`, `TheoryUF::preRegisterTerm` |
| **Outcome** | spurious; the analysis was fixed rather than the row retracted |

**What happened.** `SET_FILTER` is ungated in safe mode and the seam refuses
`SETS_FILTER_UP`/`DOWN` there, so a `set.filter` benchmark should have failed
`--check-proofs-complete`. Every link held in the source. But `set.filter` takes
a predicate, a predicate is a function-typed term, and
`TheoryUF::preRegisterTerm` throws `LogicException` on a function-typed term
unless the logic is higher-order — which safe *and* stable mode refuse.

**What we learned.** One command settled what no amount of reading would have,
and this is why carrying a rank-1 claim requires an input rather than an
argument. The lesson went into the analysis instead of the retraction:
`Fragment.requires_higher_order` now recovers that axis from the type rules and
13 kinds move to blocked, which also half-killed `s-7` and left `i-1` standing
at the kind level.

## E6: cvc5 asked whether forbidding safe mode with debug symbols is a restriction

| | |
| --- | --- |
| **When** | 2026-09-17 |
| **Kind** | positive — a design question, answered with a verifier |
| **Ours** | `dokimasia.buildmode check` — 8 conditionals, all benign |
| **cvc5** | [#12899](https://github.com/cvc5/cvc5/pull/12899), `configure.sh` |
| **Outcome** | no defect; the decision is sound and now has a check behind it |

**What happened.** cvc5's configure script forbids combining a safe build with
debug symbols — deliberate, for clarity, and #12899 flattening the build system
was the moment to ask whether it still made sense. The question worth answering
was not *why is it forbidden* but *what does forbidding it cost*, and that rests
on an invariant: **a safe build differs from an unrestricted one only in
defaults, text and reporting.** All eight `CVC5_SAFE_MODE` conditionals were
enumerated and classified; the divergence is real but lives in message text the
regression testers read, so the restriction bites only when debugging a
safe-mode skip.

**What we learned.** The shape to repeat. An opinion is worth nothing to
somebody who knows the code better than we do, and a reading of the source is
worth something once; the invariant with the verifier attached is the only
answer that survives the next edit. It also inverts the usual burden — instead
of us asserting something about their code, they get a thing that tells them
when it stops being true.

## E7: cvc5 routed us a bug report that is not a proof bug

| | |
| --- | --- |
| **When** | 2026-09-17 |
| **Kind** | neutral — a routing question, answered with a boundary |
| **Ours** | — no observation; the deliverable was scope |
| **cvc5** | [#12905](https://github.com/cvc5/cvc5/issues/12905), `theory_engine.cpp:2030` |
| **Outcome** | out of scope, with the test for the next one written down |

**What happened.** A fatal failure on a strings-and-quantifiers benchmark was
sent here. It is a real cvc5 bug. The cheap check is whether the reproducer
produces a **proof hole** — if it did, the issue would be partly ours — and it
does not. What this repository owed was therefore a boundary, not a verifier,
and the learning about how cvc5 issues actually get resolved belongs to
[Paideia](https://github.com/ajreynol/paideia).

**What we learned.** More of these will arrive, so the routing test is worth
having in writing rather than re-derived each time. A case that ends in a
boundary constrains future behaviour exactly as a verifier does, and answering
"not ours, and here is what made that decidable" is a complete result.

## E8: we reported that six proof checkers compile against the solvers they check

| | |
| --- | --- |
| **When** | 2026-09-18 |
| **Kind** | positive — our first filed finding |
| **Ours** | `f-1` / `R3`, from `dokimasia.tcb measure`, `cuts` and `why` |
| **cvc5** | `theory/*/proof_checker.cpp` |
| **Outcome** | filed as a kind C; acted on by cvc5 in `E12` |

**What happened.** cvc5's internal proof checker is the natural trusted kernel,
and its value depends on how little of cvc5 it needs to be right. The base class
is already disciplined — 12 of 13 registered rule checkers take nothing but a
`NodeManager*` — but six included the headers of the theory solvers they were
checking, putting `theory/strings/core_solver.h`,
`theory/arith/linear/constraint.h`, `theory/theory.h` and `theory/rewriter.h`
inside a surface of **179 files, 41,446 lines, 8.0% of `src/`**.

| from | include | uniquely worth |
| --- | --- | --- |
| `theory/strings/proof_checker.cpp` | `theory/strings/core_solver.h` | 3,193 lines |
| `theory/arith/proof_checker.cpp` | `theory/arith/linear/constraint.h` | 2,556 lines |
| `theory/datatypes/proof_checker.cpp` | `theory_datatypes_utils.h` | 1,027 lines |
| `theory/arith/nl/transcendental/proof_checker.cpp` | `sine_solver.h` | 809 lines |

**What we learned.** The number going down *is* the kernel argument getting
shorter, and it needs no verification tool, no build and nobody's agreement to
start — which is why this was measurable and reportable long before anything
else here was. The report's account of *why* each edge existed was partly wrong;
that is `E11`.

## E9: cvc5 documented the argument `SUBS`'s checker had always read

| | |
| --- | --- |
| **When** | 2026-09-19 |
| **Kind** | positive — an observation closed, citing us |
| **Ours** | `dokimasia:398b7ed5b492831606d98491` (`SIG0003`), register row `i-21` |
| **cvc5** | [#12948](https://github.com/cvc5/cvc5/pull/12948), `6e62c7cf595273b7fdfdc0a607aa53a8555530ee` |
| **Outcome** | closed; the pull request reads *"Based on an initial pass from ajreynol/dokimasia"* |

**What happened.** cvc5's substitution proof rule takes a third argument that
selects how the substitutions are applied, and its reference documentation
described only two. The `\inferrule` block read
`\inferrule{F_1 \dots F_n \mid t, ids?}` while
`BuiltinProofRuleChecker::checkInternal` had all along asserted
`1 <= args.size() && args.size() <= 3` and read `args[2]` as a second
`MethodId`. cvc5 rewrote the block to name `ida`, restated the conclusion, and
named the three modes with the termination condition `SBA_FIXPOINT` requires.
**The checker was not touched; the documentation was brought up to it.**

**What we learned.** `SIG0003` compares two partial parsers — LaTeX on one side,
`Assert`s and subscript reads on the other — and the worry was that a
disagreement between two approximations is an artifact. Here it was not, and the
fix landed on the side the check named. What made the row actionable is worth
copying: it named one rule, one file and two numbers to compare, so confirming
it took reading a single comment and a single `else if`. The 24 `SIG0002` rows
name a skolem and a file but no comparable discriminator, and none of them
moved.

## E10: cvc5 decided to keep proof-completeness checking an expert option

| | |
| --- | --- |
| **When** | 2026-09-19 |
| **Kind** | negative — our ask was rejected, and rightly |
| **Ours** | `i-3` / `R2`, second form |
| **cvc5** | `a960d7d7210e731cf48ad7baa6ad42fc7345b297`, reverted at `215eed21a6c8380075c46513e69181a295b6e3b2` |
| **Outcome** | withdrawn; only the assertion form of the ask survives |

**What happened.** We asked cvc5 to drop `checkProofsComplete` from the
`expert` category so the safe-mode tester could name the guarantee it tests.
cvc5 built the promotion, reproduced its effect, and reverted it: an option's
category governs **both** assignments, so making it settable in safe mode
equally permits `--no-check-proofs-complete` and
`(set-option :check-proofs-complete false)`, and `setDefaultsPre` honours an
explicit user assignment through `checkProofsCompleteWasSetByUser`. The
promotion would have turned a guarantee safe mode switches on into one a user
can switch off.

**What we learned.** **The expert refusal is the mechanism that keeps
completeness non-negotiable, and we read it as an obstacle to stating it.** We
reasoned from *the positive flag is refused* to *the option should be settable*
without asking what else becomes settable, and one `--no-` run would have shown
it — our own report set the bar it failed, at *"a maintainer can refute this in
thirty seconds."* The chain's fifth link, `explicit-completeness`, is withdrawn
from `CiModel.completeness_chain` and its `CI0002` entity retired, since it
asked cvc5 to weaken what we were auditing. The real exposure is untouched and
still worth carrying: completeness in safe mode is obtained by configuration,
and a `--proof-granularity` flag added to the tester would switch it off with no
test failing.

## E11: we corrected `tcb-001`, since for three includes the mechanism was a false positive

| | |
| --- | --- |
| **When** | 2026-09-19 |
| **Kind** | negative — ours, found by cvc5 acting on the report |
| **Ours** | `f-1`, and `Closure.cuts` behind it |
| **cvc5** | `theory/arith/proof_checker.cpp`, `theory/datatypes/proof_checker.cpp` |
| **Outcome** | corrected; `Closure.edge_use` added and the disputed edges pinned by test |

**What happened.** `E8` said six checkers included their solvers *to reach
`static` helpers parked on solver classes*. True of the strings edge. cvc5
replied that the arithmetic checker uses **nothing** from
`linear/constraint.h` and the datatypes checker nothing from
`theory/rewriter.h`: those includes were simply dead, removed in a line each,
and the helper extraction the finding proposed for them was work nobody needed
to do. The measurement could never have supported the claim — `cuts` weighed an
include by how much closure it carried and never asked whether the file used
what it included, so a dead include and a load-bearing one produced identical
rows and the prose supplied a mechanism for both.

**What we learned.** A measurement can be exactly right and still carry a wrong
story, if the tool never checked the story. `Closure.edge_use` now classifies
every edge `used`, `unused` or `unknown`, and **`unknown` is never collapsed
into `unused`** — calling a live include dead is the same error reflected.
Getting that bias right took three corrections of its own: include guards
counted as declarations, utility headers of free functions read as dead, and
filtering ubiquitous type names made `expr/node.h` look unused by a file that
plainly uses it. Each is now a named test.

## E12: cvc5 removed the dead includes and moved the strings helpers out of the solver

| | |
| --- | --- |
| **When** | 2026-09-19 |
| **Kind** | positive — a filed finding acted on, citing us |
| **Ours** | `f-1` / `R3`, and the `edge_use` classification from `E11` |
| **cvc5** | `theory/strings/proof_checker.cpp`, `theory_strings_utils.h`, and four dead includes |
| **Outcome** | the measured closure falls from 179 files / 41,448 lines to **141 / 31,541** |

**What happened.** cvc5 removed all four dead includes — including the two
`E11` surfaced after the classification was added — and separately extracted the
live dependencies: `getConcatConclusion`, `getDecomposeConclusion`,
`getExtensionalityConclusion`, `getSufficientNonEmptyOverlap`, `eagerReduce` and
`lengthPositive` moved to `strings::utils`, so the strings checker no longer
includes `core_solver.h` or `term_registry.h`. Validated with byte-for-byte
identical CPC proofs on five benchmarks and 525 passing regressions, and cvc5
re-ran `dokimasia.tcb measure` to report the result.

**What we learned.** The check was pointing where it claimed, and the part cvc5
could act on immediately was the part that named a file and a line rather than a
refactoring. cvc5 states plainly that this does not establish a smaller *runtime*
trusted computing base — the compile-time surface is what moved — and that
distinction is one we should make in our own wording before they have to.

## E13: a cvc5 rename disarmed one of our checks, silently

| | |
| --- | --- |
| **When** | 2026-09-19 |
| **Kind** | negative — ours, triggered by an ordinary cvc5 change |
| **Ours** | `Job.mode` in `dokimasia/ci/scan.py` |
| **cvc5** | [#12899](https://github.com/cvc5/cvc5/pull/12899) and [#12906](https://github.com/cvc5/cvc5/pull/12906), renaming build types |
| **Outcome** | open — the heuristic still keys on the old spelling |

**What happened.** Reading a window of cvc5 history for closures, the `ci` check
reported *"a build job runs in safe mode: none"*. cvc5 had not removed safe-mode
CI. `Job.mode` keys on the literal substrings `safe-mode` / `stable-mode` in a
matrix `config:` value, and cvc5 renamed those values to `safe` / `stable`. The
safe-mode job is still there and still runs `--tester proof`; the check now
classifies every job `unrestricted`, which disarms `CI0001` and makes two links
of the `CI0002` chain read `NO` for a reason that has nothing to do with cvc5.

**What we learned.** **A check keyed on a spelling cvc5 is free to change will
fail open, and this one did** — it reports less rather than erroring, which is
the failure mode nobody notices. The same window contained two more renames that
look like fixes and are not: cvc5 renamed the four CI jobs carrying every
`CI0004` row, and renamed the `InferenceId` carrying an `INFERID0001` row, in
both cases moving the condition intact under a new name. *Absence closes
nothing* caught those; nothing caught this one, and the fix is still outstanding.

## How this page is maintained

**Who writes it.** `prompts/close_bug_db`, which reads a window of cvc5 history
against the revision the observations were taken at and leaves this file and
`bug_db/bugs.json` changed and uncommitted. A maintainer reads the diff. Entries
about our own corrections are added in the run that makes the correction.

**When an episode earns an entry.** Something happened *between this repository
and cvc5*: cvc5 accepted, rejected or acted on something of ours; cvc5 asked us
a question; or a claim we published about cvc5's code turned out to be false. A
check finding nothing, a hypothesis still waiting for a verdict, and a change to
our own tooling that no cvc5 change prompted are **not** episodes — those are
the register in `docs/README.md` and the ordinary commit log.

**The template.** Copy it exactly. The next id is one above the highest ever
used, including entries that were later corrected; ids are never reused, and an
entry is never deleted or rewritten to say something else — a later entry
corrects it and links back by id, as `E11` does to `E8`.

```text
## E<n>: <what happened, as a sentence with cvc5 or we as the subject>

| | |
| --- | --- |
| **When** | the date, or what it was before if no date is recoverable |
| **Kind** | positive or negative, and in four words why |
| **Ours** | the identity, register row, or tool that carried it — or — |
| **cvc5** | the pull request, commit or files |
| **Outcome** | what state it is in now |

**What happened.** The episode, for somebody who works on neither project: no
check codes in the first sentence, and enough of the mechanism that a reader
could go and check it. Name the commit or the file.

**What we learned.** What this says about the check, the report or the
judgement behind it — what it over- or under-claimed, and what would have
caught it sooner. **This field is why the page exists.** An entry without it
records that something happened and nothing about what to do differently.
```

**Two rules that keep it honest.** Attribution is recorded and never argued:
whether cvc5 made a change because we reported it or found it independently, the
check was pointing at something real either way, and only the first is also
evidence that the *reporting* works. And a closure is a decision about a **cvc5
change**, never about a row going quiet — absence closes nothing, and the claim
has to be re-read in cvc5's current source rather than taken from a commit
message. `tests/test_experience.py` enforces the shape above; the closure rules
live in the launcher and are checked there.
